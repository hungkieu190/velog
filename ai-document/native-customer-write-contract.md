## 1. Approved initial compatibility boundary

Use WordPress APIs as the only native identity writer. Add a narrowly scoped native-user database adapter and shared identity guard rather than mirroring users or adding indexes to core tables.

Initial supported write environment: single-site WordPress, mysqli, verified InnoDB users/usermeta/options/posts/postmeta, ordinary core wpdb connection behavior, and no persistent object-cache or db.php drop-in. For the first adapter, VeLog must be the only active ordinary plugin and there must be no unreviewed MU-plugin. VeLog customer transactions support only reviewed core/VeLog callbacks on the user, metadata, option and query paths they invoke. Unknown callbacks cause the customer mutation/migration preflight to fail with storage_unavailable before a user write; never remove or suppress those callbacks globally. Ordinary non-customer login and unrelated administration continue normally. A site requiring other user integrations or cache/database drop-ins needs a separately tested adapter before customer writes are enabled.

This restriction is explicit and material. It is not an assertion that the actual LocalWP installation currently satisfies it. Preflight must report the unsupported component to an authorized manager without exposing credentials. Do not claim compatibility from PHP/WP versions or the absence of one particular user_register callback.

## 2. Native identity guard

Register a final `wp_pre_insert_user_data` guard for native wp_insert_user/wp_update_user calls. At the native SQL write boundary, acquire a database-scoped named mutex derived from a hash of database/site identity (maximum 64 ASCII bytes), with a five-second timeout. Re-read login/email directly under lock using the users table's actual collation and prepared queries. For updates, exclude only the exact target native user ID. Also check login-versus-email authentication ambiguity: no customer login may equal another account's login email, and no customer email may equal another account's login; report such existing data during preflight. Do not mutate supplied identities to avoid conflicts.

The lock applies to supported native API writers, including WordPress Users administration, REST, CLI and import paths that load VeLog normally. Core import flags cannot bypass the final check. CLI with the plugin skipped, direct SQL, another connection performing raw writes, or callbacks deliberately overriding the final guard are outside the supported writer boundary; detect ambiguous customer identities on read/auth and fail closed. No plugin can enforce integrity against code that bypasses all of its hooks; document that trust boundary explicitly.

For native writes outside a VeLog transaction, release only after user_register/profile_update has completed the guarded database write; on error/exception, release in shutdown/connection cleanup. Use ownership/depth tracking so nested calls cannot release a caller's lock. For VeLog operations, the coordinator owns and releases it after commit/rollback and cache cleanup. Explicitly verify lock ownership and connection identity before success. The retained prototype holds its lock until request shutdown; production release/depth tracking is still to be implemented and tested.

On conflict/timeout, return an empty data array so the native API safely refuses its write; retain typed context internally for VeLog errors duplicate_identity/identity_ambiguous/storage_unavailable. Generic native callers receive a safe rejection, never a fake successful user ID. Reject unmanaged edits to existing VeLog customers through the same boundary; do not let native profile screens bypass version/state/audit. Native password-reset writes require the separately validated reset context.

## 3. Scoped API connection and transaction

Proposed `NativeCustomerConnection extends wpdb` overrides check_connection/db_connect while a write transaction is armed; it refuses reconnect instead of allowing core to replay a failed write on a new autocommit connection. Never use reflection to change core protected reconnect_retries or patch WordPress core.

The coordinator creates this connection with the configured native database settings, validates database/table/prefix identity, and passes native API calls through it by temporarily binding the global wpdb in a strictly synchronous try/finally scope. Restore the exact prior object in finally and shutdown cleanup. Do not keep the adapter globally installed or change it from an arbitrary authentication hook. Reject foreign database adapters, nested transactions and unsupported callbacks before binding.

Acquire locks in this order everywhere: native identity mutex, then the same shop-wide DATA-001 coordinator row lock, then target user/meta rows in ascending ID order. Vehicle relation mutations must participate in the same order after their contract is rebased; do not introduce a second unrelated archive lock. Prepare the shop lock outside the transaction. Enforce a five-second row-lock timeout and restore connection session settings.

Start the transaction on the adapter's pinned handle. Read native row and exact metadata snapshots; verify actor, customer schema/role, expected version, request ID, identity uniqueness and current relations. Native user create/update uses wp_insert_user; metadata uses core metadata APIs; audit/request entries use native option APIs. Verify the final raw rows, role, version and ledger on the same handle, because some API paths do not reliably report every underlying write error. Reject unexpected SQL statement classes and transaction control from callbacks. A positive native user ID alone is not success.

No network, filesystem or mail effects are permitted inside the transaction. Runtime callback preflight must cover user_register/profile_update, user field/meta filters, role hooks, generic metadata hooks, option hooks, query hooks and reachable cache callbacks; a short static hook list alone does not prove arbitrary third-party safety. Keep WordPress locale caches/role state initialized before binding, and recheck the supported callback registry at the write boundary. Unknown code is not made safe by catching its exceptions.

On known pre-commit failure: rollback on the same live handle, invalidate native user/login/email/user_meta and touched option/alloptions/notoptions caches, restore the original wpdb, and release only owned locks. On commit success: verify durable request result through a fresh connection before returning success; perform equivalent cache cleanup, then post-commit external effects. Track both old and new identity lookup keys for cleanup. Object-cache drop-ins remain unsupported until their cross-request cache behavior is proven.

On lost/ambiguous COMMIT response: do not claim rollback or retry with a new request ID. Restore/close the adapter, clean caches, and use the durable request row on a fresh connection to reconcile committed versus absent. If reconciliation itself fails, return outcome_unknown with the same request ID and deny affected mutations until resolved. Readers/auth must use authoritative valid database state and reject corrupt or ambiguous customer identities. Crash/fatal shutdown cleanup is best effort; the database owns rollback on connection close, and persistent shared cache is outside this initial compatibility contract.

The prototype verifies basic rollback/commit and reconnect refusal only. Callback preflight, nested lock release, state/audit snapshots, post-commit reconciliation and all HTTP/auth paths still need production implementation and tests.

## 4. Metadata and ledger layout

No custom table is required in this candidate. Native names/login/email exist only in native WordPress storage. Do not create a new record envelope with copied current identity fields.

| User meta key | Exact representation |
|---|---|
| `_mf_velog_customer_schema` | Canonical ASCII `1`, exactly one row |
| `_mf_velog_customer_state` | Exactly one row containing pending/invited/active/archived |
| `_mf_velog_customer_version` | Exactly one canonical positive base-10 integer string; bound to PHP_INT_MAX and reject overflow |
| `_mf_velog_customer_phone` | Exactly one validated UTF-8 string, empty allowed, at most 64 characters |
| `_mf_velog_customer_invitation` | Absent or one serialized closed-schema array: schema=1, generation UUID, verified actor ID, verified UTC instant, attempt UUID, status prepared/sent/failed/unknown, expires UTC instant and email HMAC; no raw reset key or URL |
| `_mf_velog_customer_legacy_id` | Absent or one canonical positive integer string; migration provenance only |

All row counts, PHP types after deserialization, enum values and bounds are validated strictly. Role capabilities remain native WordPress data, not duplicated in VeLog meta. No missing role/meta is silently repaired on login.

Durable event/request row: non-autoloaded option `mf_velog_customer_event_<request UUID>`, unique through the native option_name key. Closed serialized array: schema=1, request UUID, action, actor ID, native user ID, UTC instant, expected/result version, changed field-name list, bounded reason, payload HMAC, and outcome containing only native ID/version/state. Audit is append-only through the domain API; no database-administrator tamper-proof claim is made. No plaintext name/login/email/phone/password/reset URL is copied into this row. HMAC uses the site's authentication salt; a changed salt causes safe replay conflict and explicit remediation, never blind re-execution. Retain events on uninstall; no pruning policy is introduced.

Migration rows: non-autoloaded `mf_velog_customer_migration_<run UUID>` for closed-schema run state/cursor/counts, and `mf_velog_customer_map_<legacy ID>` for unique schema=1/run/source ID/native ID/source fingerprint/item state/relation schema. Row uniqueness is option_name, not usermeta. Manager-reviewed remediation input is namespaced private run metadata, never a parallel ongoing identity store. Delete the completed item's temporary remediation login/email/name values in the same transaction that commits its verified native target and mapping; retained run/mapping/audit data contains IDs/fingerprints/counts only. Pending or conflicting remediation input remains private until explicit manager discard or successful apply, with no scheduled silent cleanup. List/query audit and mapping rows through bounded indexed name-prefix/range queries, never an unbounded autoloaded array. Migration checkpoint/source mapping, native account and initial event commit in one transaction.

Source relation inventory: current RecordSchema defines vehicle `fields.current_customer_id` and `_mf_velog_current_customer_id` as the operational references. Service and reminder field definitions are currently empty; do not invent existing service-customer columns. Dry-run must verify actual persisted envelopes against this inventory and refuse unknown schema fields/references rather than skip them. Rebase the current-owner field/projection with an explicit relation schema version, retain old audit snapshots as typed legacy history, and preserve original values. This is source inventory only; no active-site data has been inspected.

## 5. Service and error contract

NativeCustomerService receives the actor from trusted request context, never an actor ID supplied by a form. Proposed public methods: create(fields, actor, request_id); update(id, expected_version, fields, actor, request_id); archive/restore(id, expected_version, actor, request_id); invite(id, expected_version, actor, request_id); get_summary(id, actor); query(criteria, actor). Mutation output is ID/version/state, never WP_User or credentials. Query page size is 50; allowlisted sort display_name/ID with ID tie-break and bounded prepared criteria. Contact search uses authorized POST and a short-lived per-user opaque search token in non-autoloaded transient storage; token contents must not appear in public URLs or evidence.

Fixed internal codes: forbidden, invalid_input, duplicate_identity, identity_ambiguous, stale_version, request_conflict, active_vehicle_link, invalid_customer_state, storage_unavailable, integrity_conflict, outcome_unknown, invitation_failed. HTTP handlers map only these to safe translated notices; they validate exact action-specific nonces, scalar shapes and capabilities before service calls. Service methods repeat authorization for direct callers. Bulk operations report each item separately.

## 6. Invitation delivery and reset completion

Preparation commits an audited current invitation generation and native reset-key hash, while the customer stays pending for a first invitation; no raw key is persisted outside native core's allowed mechanism. Use core reset-key APIs in the controlled context, retain the raw link only in memory until post-commit mail handoff. Sending happens after commit. Only successful handoff followed by a verified versioned finalization changes the first invitation to invited. If delivery is rejected, record failed and remain pending. On process loss after handoff, report unknown; do not promise exactly-once mail, activate the account, or resend the same persisted raw link. A manager retries with a new generation which invalidates the old key. No external delivery is authorized by these tests.

For re-invites, revoke the previous generation during preparation and ensure the account is denied until finalization; do not reuse an already accepted attempt's request ID as a new send. Archive/email change invalidates the generation, key and sessions. Reset completion must recheck invited state, generation, unchanged email, expiry and expected version before allowing password mutation. Validate errors at the native reset validation boundary. Coordinate the native password mutation with active transition/audit using the supported connection/callback boundary; post-reset notification is after commit. If native reset integration cannot meet this, keep that gate open rather than accepting a successful after_password_reset callback as proof.
