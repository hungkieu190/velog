## Independent assessment

- **D1-F-013:** The proposal keeps the pinned four-argument API, 50-item pages and error vocabulary. Fixed state/visibility projections and a shared prepared predicate support exact count and bounded page IDs under the approved VeLog-writer integrity invariant. `GROUP BY p.ID` prevents join multiplicity from consuming page slots; page ID preflight and batch hydration fail closed on duplicate or inconsistent selected rows. The post-author equality is an invariant of the approved direct insert plus immutable post row, and must be checked against `created_by` for every hydrated service row. Count exactness for externally corrupted rows outside the page is not claimed.
- **D1-F-014:** Prepared tuple joins on the pinned handle, candidate and target envelope checks, and absent-projection zero-row handling address the prior design failure. The same registered projection derivation must be used by writes and verification.
- **D1-F-015:** Revision 5 uses `mf_velog_create_<sha256(request_id)>`, `payload_fingerprint`, `hash('sha256', serialize($canonical))`, and audit `request_id_sha256`. A fresh lock and same-request-ID retry rule address ambiguous creates/saves. Rollback classification requires the original connection identity and confirmed rollback.
- **D1-F-016:** Revision 5 names per-statement fault points, distinguishes committed/lost acknowledgement from pre-commit disconnect, and truthfully labels an unproven live-handle COMMIT failure and application 1213 control `NOT VERIFIED`. Those labels are accepted for starting implementation, not as passing contract evidence or permission to close DATA-001.

## Binding implementation and review constraints

1. The proposed `SELECT meta_key, meta_value, COUNT(*) ... GROUP BY meta_key` is not a valid exact-value oracle when multiple values exist and may fail under `ONLY_FULL_GROUP_BY`. Fetch the bounded candidate/target rows, group in PHP, then require exact expected key set, cardinality and scalar values. Include `_mf_velog_record` separately. The page preflight must check both duplicate and missing required projections for selected IDs; page hydration must compare `post_author`, envelope `created_by`, state and visibility context/projections before any snapshot is returned.
2. Any fault setter or executor seam must be unreachable in production and from request data. Gate it to the disposable test bootstrap before plugin load; reset it after each test. It must wrap the actual pinned-handle statement/COMMIT call, record that the named fault was hit, and never replace the database operation with an assumed successful mock. Failure after a real statement and lost acknowledgement after a real COMMIT need separate raw database oracles. A public, generally callable production `set_test_statement_fault()` is **not approved**.
3. Reconciliation must validate the entire envelope/audit structure before inferring a gap-free version sequence. Compare `request_id_sha256`, actor, operation, expected version position, and canonical before/after values. Marker mismatch proven to be request-ID reuse returns `conflict`; malformed/uncertain data returns `indeterminate`. A missing marker or unchanged version permits only a retry with the same request ID after successful reads under the fresh lock. Cache-invalidation or timeout-restoration failure must override a would-be success without masking a pre-existing `indeterminate` result.
4. The reported live-handle COMMIT-failure and coordinator 1213 controls remain **NOT VERIFIED**. They do not count as passing V4 or DATA-001 acceptance. Preserve a real database-only 1213 probe as separate evidence and the measured coordinator 1205 control. If a safe, reproducible pinned-handle control becomes available, run it on both disposable WordPress versions; otherwise report the exact gap and do not claim full V1–V5 verification. Persistent-cache compatibility and G-08 product performance also remain **NOT VERIFIED**.
