# DATA-001 candidate execution contract — revision 2

This is an Architect blueprint companion, not implemented behavior. It narrows the choices available to a Builder once DATA-001 is approved.

## Public Common API

- `RecordSchema::register(string $post_type, array $definition): void` is callable only from trusted bootstrap code. Definitions provide fixed field validators, fixed projection keys, state rules, capability actions and a context builder for `AccessPolicy`. No definition is inferred from request data. The registry is closed before repository use. An unregistered type fails closed.
- `RecordRepository::get(string $type, int $id, WP_User $actor): array|WP_Error`; `query(string $type, array $filters, int $page, WP_User $actor): array|WP_Error` return validated, authorized snapshots only. Query page size is 50 maximum and uses stable ID tie breaking. Never return raw `WP_Post`/unfiltered postmeta to an HTTP caller.
- `create(string $type, array $fields, WP_User $actor, string $request_id): array|WP_Error` and `save(string $type, int $id, int $expected_version, array $changes, WP_User $actor, string $request_id, string $reason = ''): array|WP_Error` accept only domain fields. `request_id` is a caller-generated UUID; it cannot select record IDs or meta keys. The method returns the committed snapshot or a stable `WP_Error` code (`invalid_input`, `forbidden`, `not_found`, `stale_version`, `conflict`, `storage_unavailable`, `indeterminate`). The caller must not auto-retry `indeterminate` with a fresh request ID.
- `WriteCoordinator::run(WP_User $actor, callable $trusted_operation): array|WP_Error` is an internal trusted-code API for same-transaction related writes. It exposes a narrow unit object to re-read, create and save; nested units and direct callbacks from form input are rejected. Later domain services own relation and business-state validation.
- `AuditEntry` is generated by the repository from `actor->ID`, UTC instant, request ID, reason and before/after field snapshots. Input cannot supply or replace audit entries. No public hard-delete method.

## Storage map

- Private post types remain the four accepted CORE-003 slugs. Insert one `wp_posts` row per record with post type from the closed registry, `post_status=private`, `post_author=actor ID`, local and UTC timestamps, closed comments/pings, and no public slug or content. The authoritative business state is in meta, not the WordPress post status. No later record save mutates the post row. The direct insert explicitly supplies all required columns; Builder verifies the column map against WP 6.4.3 and 6.7.2 schemas before implementing it.
- Exactly one `_mf_velog_record` meta row holds the versioned envelope and typed fields. Exactly one row per registered projection key is maintained; absent projections have no row. Reject duplicate authoritative/projection rows. Use WordPress-compatible serialization with strict decoding to arrays/scalars only; never instantiate input-provided objects. Meta registration is protected, `single`, `show_in_rest=false`, with a deny-by-default native auth callback. Repository authorization is separate.
- A non-autoloaded `mf_velog_write_lock` option row is the transaction-scoped serialization target. A non-autoloaded `mf_velog_create_<sha256(request_id)>` option stores type, created ID and payload fingerprint in the same transaction as a create. Its indexed unique `option_name` and the row lock prevent duplicate retry results. Update request IDs are recorded in audit entries; on an ambiguous result, re-read under a fresh unit and match ID/version/request ID before returning a result. Do not garbage collect these keys in DATA-001.
- Registry-defined projections are derived from the authoritative envelope and written in the same transaction. Proposed keys in the draft queue are not activated until the owning entity task defines their normalization and policy. Repository lookups use allowlisted prepared joins and post type/status checks. The G-08 dataset is a future benchmark, not a reason to implement unapproved vehicle/reminder semantics now.

## Transaction and cache sequence

1. Authenticate/authorize and validate scalar inputs. Check single-site mode, MySQL/MariaDB `mysqli`, no caller transaction, and InnoDB for the site's posts/postmeta/options. Fail before product mutation when unsupported. Create the fixed lock option idempotently with `autoload=no` outside a product write unit.
2. Pin the current `mysqli` handle and connection ID. Save the session's lock-wait timeout; set it to five seconds; `START TRANSACTION`; `SELECT option_id ... FOR UPDATE` on the fixed lock row. Only one returned row is success. A timeout/deadlock rolls back and returns retryable `conflict`.
3. Under that lock, re-read records directly from the pinned handle. Re-evaluate policy, expected versions, idempotency and registered uniqueness. Construct the new full envelope, append one audit entry, and derive all projections. Execute prepared plugin-owned post/meta/options SQL through the same pinned handle only. Never call `$wpdb->query()`, `wp_insert_post()`, `update_post_meta()` or a callback which can issue transactional writes through `$wpdb` within this unit: local WordPress core may reconnect and retry a statement outside the locked transaction.
4. Verify row counts, serialized payload, projections and option markers on the pinned handle, then `COMMIT` exactly once. On an error before commit, `ROLLBACK`; on lost acknowledgement, return `indeterminate` and reconcile under a new lock before any retry. Do not run external hooks, mail or network operations inside the transaction. Restore the session timeout if the connection survived.
5. In `finally`, invalidate every affected post/meta cache on either path; repository canonical reads bypass WordPress object cache. The disposable WP probe demonstrated that `get_post()` can otherwise retain a rolled-back row. A supported persistent cache must honor WordPress invalidation APIs; exercise a warmed cache in integration tests. Return no false success when invalidation or connection state is uncertain.

## Required implementation verification

- Unit: schema/field/actor spoofing, regional exact values, audit immutability, unknown schema, unique projection derivation, stable errors and pagination.
- Isolated WP 6.4.3 and 6.7.2: actual post/meta/options engines and row map, two writers contending, stale version, identical/different request-ID retry, unique-key collision, multi-record rollback at each statement, warm post/meta cache after commit/rollback, connection kill before and after commit, row-lock timeout/deadlock, reactivation and uninstall retention. Each negative mode must prove its intended validator and leave no owned process/directory behind.
- Record raw commands, exits, versions and per-case state in portable evidence. `composer run lint`, `composer run test -- --display-skipped`, shell syntax, `git diff --check` and `git diff --cached --check` must pass. G-08 full p95 is NOT VERIFIED until domain list/search queries exist.

## Boundaries and remaining risk

- The coordinator guarantees VeLog-owned rows when all VeLog writers use it. Direct writes by another plugin to these private records are unsupported and must be detected where possible. External side effects of third-party hooks are outside the transaction; the coordinator avoids invoking WordPress write helpers and after-write hooks inside the unit.
- The local spike proves the candidate primitives, not the complete repository or persistent-cache compatibility. A Builder must return an architectural gap before writing application code if the pinned connection, WordPress table shape, cache contract or host database cannot satisfy these rules. No weaker fallback is permitted.
