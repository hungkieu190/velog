## Decision-complete corrections for the escalated scope

### D1-F-013 — bounded authorized query and exact count

`proposal.md:26` adds `$per_page` to the pinned four-argument `query()` API without an approved contract change. Keep the public signature and the existing 50-item page size. `proposal.md:41-65` offers a SQL count for three types, but the optional state lives in the envelope; the service branch reads every serialized audit envelope to calculate an exact total, and its stated candidate-window cap cannot yield an exact total or fill later authorized pages. Only page-slice corruption is checked; the count can include records without a valid authoritative row.

Use one fixed, protected, scalar query projection for state and one for every actor-independent object-read predicate actually needed by `AccessPolicy` (service state, positive author, vehicle visibility). Derive and verify these alongside `_mf_velog_record` within the same pinned write unit. No request-supplied SQL, keys or callbacks. For query, check actor read capability first; use allowlisted prepared SQL predicates over the fixed projections for `COUNT(DISTINCT p.ID)` and a separate ordered `p.ID ASC LIMIT 50 OFFSET ...` ID page. Apply state filtering in both SQL statements. Hydrate only that ID page in one batch; require exactly one authoritative row and exact required projection cardinality/value for each returned ID, then re-run `AccessPolicy::authorize()` on its decoded envelope. If a row or policy result disagrees with the SQL selection, return `corrupted_record` or `storage_unavailable`, never a shortened page or success with an inaccurate total. Reject unsupported filters, page overflow and SQL errors. Prove SQL predicate equivalence for all four current types with mixed-visibility pages, state filters, page 2, duplicate/malformed page rows and a nontrivial count. If a trusted projection cannot represent the current policy without adding unapproved domain semantics, report that exact architectural gap before implementation rather than silently reverting to an all-envelope scan. A total derived from projections is exact only under the transactional projection invariant; state that limit in the implementation report.

### D1-F-014 — complete-tuple uniqueness and projection integrity

Separate inner joins on all registered keys of one tuple, bound to the same post ID/type/private status and excluding the current ID, are the correct direction. However `proposal.md:79-93` displays `%s` placeholders passed to `mysqli_query()` without a binding step. Use the pinned handle's prepared statement API (or the existing reviewed bound-query helper), with fixed allowlisted table/key identifiers and bound values; no interpolated user values or SQL error text in a caller-facing response. A failed prepare, bind, execute or fetch returns `storage_unavailable` and forces rollback.

`proposal.md:94-97` explicitly accepts duplicate projection rows, contradicting the pinned exact-cardinality invariant. Under the coordinator lock, validate every matched candidate and the target record: each registered projection key has exactly one row with the derived scalar value, and the authoritative envelope has exactly one row. A duplicate or missing required projection returns a corruption/storage error; it is not a harmless join multiplicity. Distinct `(A,B)` tuples sharing A must succeed; exact tuple collision must return `conflict`. The same checks apply on create and save, including changes to only one component of a composite rule.

### D1-F-015 — transaction result and create/save reconciliation

Confirming `ROLLBACK` success and pinned connection identity is required before a 1205/1213 result can be retryable `conflict`; rollback failure, dropped/replaced handle or unknown commit acknowledgement yields `indeterminate`. `mysqli_ping()` alone does not prove that the original pinned connection survived. The proposed `uncommitted` result code and `status => committed` response change the pinned public error/result shape; retain committed snapshots and the contract's stable errors, with safe retry represented by a documented existing error only after proof. Keep reconciliation read-only under a fresh coordinator lock and enforce actor capability/object policy before returning a snapshot.

For create, use the exact existing transactional request-ID marker format and repository fingerprint calculation. A valid marker plus matching type, ID, fingerprint, one private post, one envelope and matching projections proves commit. A missing marker proves no commit of that request only when the new lock is held and the marker/write atomicity invariant is verified; a different record sharing a unique value is not proof either way. A corrupt or mismatched marker is `indeterminate`/`conflict` as appropriate, never automatic retry with a new ID. For save, inspect the target's validated envelope and append-only audit for the given request ID, actor, expected version and change fingerprint; do not look only at the latest audit entry, because a later legitimate save may follow. Version unchanged with no matching audit under the fresh lock can allow a retry with the same request ID; version advanced without a matching entry is `stale_version` only when that state is unambiguous, otherwise `indeterminate`. Do not mutate during reconciliation. Keep cache invalidation on commit and rollback. A cache miss (`wp_cache_delete() === false`) is normal, but an invalidation exception/failure that can expose stale state must not be logged and followed by success; timeout restoration failure must also be classified without hiding a known transaction outcome. No debug logging in product code.

### D1-F-016 — executable failure controls

The proposed V2 tests stop after write 1 or write 2; they do not fail **each** statement in a multi-record unit. Enumerate the actual post, envelope, projection, request-marker and audit-related write steps, inject a failure immediately after each reachable step, and compare raw posts/postmeta/options state before and after rollback on both WordPress versions. A malformed SQL statement issued by a test callback only proves callback error handling; inject a failure in a repository/coordinator statement on the pinned handle and assert the intended error branch and no partial write. Keep fault injection test-only and inaccessible from request input.

V4 must separately distinguish disconnect before COMMIT, successful COMMIT with lost acknowledgement, failed COMMIT with surviving connection, deadlock/lock timeout, and fresh-lock reconcile for both create and save. A real connection/fault control and raw database state must identify which branch ran; do not simulate both commit outcomes with the same marker setup. Record worker exits, exact result codes, elapsed lock wait, row counts/versions, and warmed-cache reads. Preserve the negative control, V3 retention, V5 query-plan sample, full lint/unit gates and cleanup proof on disposable WP 6.4.3 and 6.7.2. Mark any unexecutable control NOT VERIFIED and keep DATA-001 out of acceptance rather than claiming a pass.
