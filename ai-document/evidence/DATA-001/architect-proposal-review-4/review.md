## Blocking corrections

1. **D1-F-013 / projection equivalence:** `proposal.md:28-34` derives service author from `created_by` but filters on `p.post_author > 0`; the pinned contract says later saves never mutate the post row, while `AccessPolicy` checks context `author` from the envelope. A mismatch between the two can change the SQL count. Either add a fixed, transactionally derived positive-author projection from the same context or prove and verify `post_author === created_by` on every path that can return a record. The current generic service context builder sets `vehicle_visible` to false when the field is absent; preserve that fail-closed behavior. `proposal.md:60-75` uses `COUNT(p.ID)` while page joins can multiply IDs if a projection key has duplicate rows. The proposed page-level check is acceptable for a selected duplicate, but state exactly how the page query detects duplicate IDs even when `LIMIT 50` cuts through the duplicate group, and how total/total_pages are prevented from being returned as exact for that request. A preflight duplicate query for the selected page IDs or grouped ID selection is required; do not silently skip/trim. Count and page must share the same authorization predicates and prepared values. This is an implementation gate, not a request for global corruption scanning on each query.

2. **D1-F-014 / candidate and target integrity:** `proposal.md:102-113` now checks a matched candidate, but it infers projection presence from a field with the same key name. Registered projections are derived by a schema rule and can be absent even when an input field exists. Compute the expected projection map using the same trusted derivation as writes, then compare exact key set, cardinality and values for the candidate and the current save target. An optional absent projection requires zero rows. Do this under the coordinator lock before returning `conflict` or accepting the save. Keep prepared tuple joins and `storage_unavailable` on any SQL failure. This correction is bounded to the records touched by the uniqueness check; it does not require a table-wide integrity sweep.

3. **D1-F-015 / actual marker and audit shape:** `proposal.md:142-146` correctly names `mf_velog_create_<sha256(request_id)>`, but the serialized marker contains `payload_fingerprint`, not `fingerprint`; use the exact key and `hash('sha256', serialize($canonical))` calculation from `RecordRepository.php`. `proposal.md:159-163` searches for raw `$request_id`, while `AuditEntry::to_array()` stores `request_id_sha256`; compare the hash, actor ID, operation and before/after values. Verify that the matching audit event corresponds to the expected version via its position in a validated, gap-free audit/version sequence or add a precisely specified internal version field to future audit entries with compatible handling for existing records. Do not treat a matching hash elsewhere in malformed history as proof. The proposed same-request-ID retry after a missing create marker is valid only while the fresh global lock is held and marker/post atomicity and SQL-read success are confirmed. State the exact handling of marker mismatch (`conflict` for proven reuse, `indeterminate` for corrupt/uncertain state). `finally` must never return a success after a known cache invalidation exception or failed timeout restoration; describe result precedence explicitly, without treating a normal cache miss as failure.

4. **D1-F-016 / executable fault evidence:** `proposal.md:192-199` says a test wrapper will inject after each `mysqli` statement, but does not identify an actual seam in `RecordRepository`/`WriteCoordinator`; a callback after the entire `WriteUnit::create()` cannot reach intermediate SQL steps. Name the test-only injection point and how it is disabled in production, or use a real database fault that targets each statement. `proposal.md:207-211` simulates failed COMMIT with a live handle and a successful COMMIT with a lost acknowledgement through an unspecified wrapper. Define the wrapper's exact call/return behavior and raw database oracle so it cannot report a mocked pass without executing real COMMIT on the pinned connection. `proposal.md:216-218` deadlocks two arbitrary option rows, but every VeLog write unit first locks the single `mf_velog_write_lock` row; that scenario cannot drive `WriteCoordinator` to observe 1213 as claimed. Use an additional lock cycle reachable from the actual pinned coordinator path (without bypassing the global lock), or report this specific 1213 application control NOT VERIFIED while retaining a genuine database-only deadlock probe as separate evidence. Keep 1205 separate. Cover create and save, every reachable write statement, worker exits, exact error codes, rollback and raw rows on both disposable WordPress versions. An unsupported control cannot be marked PASS.
