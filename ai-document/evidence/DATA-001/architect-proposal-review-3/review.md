## Required corrections

1. **D1-F-013 / query authorization and count:** `proposal.md:27-31` derives `_mf_velog_vehicle_visible` from an unspecified vehicle relationship, although DATA-001 excludes service relationship/domain rules. Current `RecordSchema::build_context()` derives service visibility from the envelope's `fields.vehicle_visible` (currently defaulting to true) and service author from `created_by`; the proposal instead uses `post_author` and a new relationship-derived bit. These predicates are not proven equivalent, so SQL may include a record that `AccessPolicy` rejects or exclude an authorized record. Define the fixed projection strictly from the same trusted context builder and validated envelope as `authorize_read()`, with explicit fail-closed behavior when that context cannot be represented. Do not introduce a new vehicle relationship rule. Show the exact equivalence and negative tests for service visibility, author and state. Use the same prepared SQL predicate for count and page. `COUNT(DISTINCT p.ID)` masks duplicate projection joins and page SQL can return duplicate IDs; specify how duplicates on the requested page fail closed without a short/duplicated page, and state the supported transactional-integrity boundary for rows outside that page. Keep the pinned error vocabulary (`invalid_input`, `forbidden`, `storage_unavailable`, etc.) rather than introducing `invalid_page`, `unauthorized`, or `invalid_filter`.

2. **D1-F-014 / uniqueness integrity:** The prepared tuple join is directionally correct, but `proposal.md:116-121` checks cardinality only in `verify_write()` for the record being written. It does not detect duplicate/missing projections in a pre-existing candidate encountered by the uniqueness query, and checks counts without comparing each value to the authoritative envelope. Define a pinned, under-lock candidate verification path before treating a match as `conflict`: one authoritative envelope, exact required projection cardinality, exact derived values, and type/status. Corruption is not a valid collision. Apply the same checks to the write target and exclude its ID on save. Clarify how an optional/absent registered projection is handled under the pinned rule (“absent projections have no row”); a blanket count of one for every registered key is wrong. Preserve the strict SQL-failure result and prepared bindings.

3. **D1-F-015 / reconciliation:** `proposal.md:148-150` names `_mf_velog_req_...` and JSON hashing, while current create code stores `mf_velog_create_<sha256(request_id)>` and fingerprints `serialize($canonical)`. Use the exact production marker format and canonicalization, or explicitly map a compatible migration within scope. The missing-marker check at line 156 asks for a post row “with that request marker”, but the approved storage map has no request marker on posts; explain the actual proof available under the fresh lock, without inferring no commit from a unique-value search. `not_found` must not be described as a general safe-retry certificate: define retry only with the **same request ID**, after marker atomicity and authoritative checks; collision and corruption remain distinct. For save, current audit stores a request-ID hash plus before/after fields but no explicit change fingerprint or expected version. Specify how those are verified from the existing audit shape or describe the exact internal audit addition. A later valid save can follow the ambiguous save: returning the latest snapshot is acceptable only after the matching historical audit entry is verified and current object authorization is rechecked. Reconciliation must use a fresh pinned connection and lock; its reads must not mutate product rows. Explain how a `finally` failure replaces an otherwise successful return, including timeout restoration and cache invalidation, without assuming `wp_cache_delete() === false` means failure.

4. **D1-F-016 / fault controls:** `proposal.md:194-200` proposes a test callback wrapper after nominal steps, which may not prove failure of the actual repository SQL statement or rollback at each statement. Map each reachable create/save statement to a narrowly scoped, test-only fault point on the pinned handle; assert the fault point was hit, expected error code, rollback outcome and raw posts/postmeta/options before/after. `proposal.md:207-209` suggests MySQL/MariaDB deferrable constraints or trigger errors *at COMMIT*; the fixture has no such mechanism. Supply a reproducible fault that distinguishes (a) pre-COMMIT disconnect, (b) successful COMMIT with lost acknowledgement, and (c) COMMIT failure with a surviving connection, or mark an unexecutable branch NOT VERIFIED. A normal successful create/save followed by a dropped application response is only a reconciliation control, not proof that `WriteCoordinator` classified a lost COMMIT acknowledgement. The proposed “deadlock” case is only a lock timeout; specify a genuine two-connection deadlock with observed 1213, separately from observed 1205. Include both create and save reconciliation, warm-cache reads, worker exit codes and raw database state on WP 6.4.3 and 6.7.2.
