## Required corrections to proposal revision 2

1. **F-002 — exact settings envelope and CAS.** `ShopSettings::SCHEMA_VERSION` is the string `1.0.0`, not integer `1` (proposal line 7). Specify exact validation for every stored field, including `catalog_version`, `configured`, `record_version`, catalog-derived `currency_scale`, and allowed currency/unit values. Treat a database read failure separately from a missing row using `$wpdb->last_error`; use a prepared query and safe deserialization without object instantiation. Reconcile the proposed `WP_Error` result with the current `get_settings(): array` declaration and all callers, including `require_configured()` and the admin form. A raw string in `WHERE option_value = %s` is not a byte-exact comparison under a typical text collation; specify a binary comparison and prove case-different bytes cannot match. Define insert/update conflict versus SQL failure results and option-cache invalidation. Explain how unrecognized stored keys are handled without silent data loss.
2. **F-002 — submitted values.** Define canonical nonnegative integer parsing for `record_version`, bounded against overflow, before casting. Validate nonce, unit, code, and region types before WordPress string functions or sanitizers; reject array/object input without warnings or writes. Distinguish invalid stored configuration from invalid submitted configuration in error codes. The proposed redirect with `error=invalid_input` must use a fixed, allowlisted value and be reconciled with the existing transient notice/redirect behavior; no submitted content may enter the URL.
3. **F-004 — concurrency oracle.** The proposed workers issue SQL `UPDATE` directly, so they test their own query rather than `ShopSettings::save_settings()`. Add a test seam or process barrier at the service read/write boundary so two independent WordPress processes call the public save path with the same prior version. Use an explicit two-party barrier with timeout and failure propagation; a timestamp threshold does not establish both have read the old row. Assert one success, one stale/conflict result, final raw row/version and cache-visible settings, with nonzero outer exit on any deviation.
4. **F-004 — historical oracle.** The default `mf_velog_service` schema registers an empty field allowlist in `RecordSchema::register_defaults()`; `validate_fields()` rejects `vehicle_id`, `customer_id`, `odometer`, and `type` from proposal line 22. Supply an isolated, valid schema registration before the registry is sealed, with validators and a valid actor, or identify a different valid repository seed. Show the returned snapshot ID and exact authoritative meta row. The seed must actually contain canonical distance and currency/scale identity if byte equality is to prove those properties; otherwise state the product contract gap and add an appropriate valid record fixture. Exercise km/mi, JPY/USD/KWD, and locale changes, and assert the complete stored envelope and interpreted historical values. Include the POST denial/nonce and uninstall/reinstall retention controls from the approved verification matrix, or mark unsupported cases `NOT VERIFIED` with a reason.
5. **F-005 — lint and owned-resource cleanup.** Tie each planned PHPCS change to an actual lint finding and check the proposed `custom_capabilities` property syntax against the installed sniff before broadening the ruleset. Identify the exact direct-query sniff(s) for each CAS statement and suppress only those lines if justified. The proposed `rm -rf "$TMP_DIR"; kill $(jobs -p)` trap is insufficient: define how the runner establishes ownership and a nonempty, unique temp path, waits/reaps only its child PIDs, removes only its own WordPress/database fixtures, and performs cleanup on success and failure. Log command versions, exit codes, manual observations, and explicit `NOT VERIFIED` items in the new implementation round's evidence directory.
